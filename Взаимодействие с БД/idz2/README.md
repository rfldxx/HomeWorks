Для одного и того же объёма данных и одного и того же алгоритма (hash join) колоночная СУБД не проигрывает строчной. 


Но надо пониммать:
Проблема в том, что JOIN требует случайного доступа, а column store оптимизирован под последовательное чтение. Маленькие правые таблицы (справочники, dimensions < миллиона строк) — ClickHouse строит hash-таблицу в RAM и стримит левую. Работает быстро.

1. ClickHouse так не делает
ClickHouse не выполняет вычисления на сжатых данных. Он распаковывает колонку в блок по 8192 значения (гранула), обрабатывает векторно, выбрасывает, идёт дальше. Это осознанный инженерный выбор: распаковка в блок — последовательная и дешёвая, а код получается проще, чем «compute on compressed».

Так что «физически распаковать» — это не математическая необходимость, а конкретно реализация ClickHouse.

2. RLE — не единственный кодек
ClickHouse по умолчанию использует LZ4 — это байтовый компрессор общего назначения, а не RLE. На LZ4-сжатых данных ты не можешь работать напрямую, потому что там нет логической структуры «значение + счётчик». Только распаковка.

Плюс есть Delta, DoubleDelta, Gorilla, T64 — каждый со своей логикой. Часть из них поддерживает частичные операции, часть — нет.

3. JOIN ≠ агрегация
Вот главное. Даже если бы ClickHouse умел работать на RLE-данных, JOIN требует случайного доступа по row index, а не просто прохода по runs

Если бы использовалось RLE то теоретически можно было улучшить эффективность JOIN, но надо было бы вводить B-tree индексов на колонках и это бы вызвало увелечения константы по всему ClickHouse, чем просто машиная обработка чанков.


Разреженный первичный индекс (Sparse Primary Index)
Вот главная оптимизация ClickHouse. Для каждой гранулы в primary.idx хранится одна запись — значение первичного ключа первой строки этой гранулы.

text
primary.idx:
  гранула 0 → (category='Books', hour=2024-01-01 00:00, status='paid')
  гранула 1 → (category='Books', hour=2024-01-01 01:00, status='paid')
  гранула 2 → (category='Electronics', hour=2024-01-01 00:00, status='paid')
  ...
Следствия:

Индекс крошечный. Одна запись на 8192 строки. Для миллиарда строк — ~122 000 записей. Такой индекс целиком помещается в RAM (загружается при старте).

Поиск быстрый. Для запроса с фильтром по ORDER BY ClickHouse делает binary search по primary.idx и определяет, какие гранулы могут содержать нужные данные. Остальные пропускает (granule pruning).

Затем читает только выбранные гранулы. По .mrk файлу находит byte offset гранулы в .bin, распаковывает её и обрабатывает.

Алгоритмически это как разреженный индекс в B-tree: ты не индексируешь каждую строку, но по ключу находишь нужный блок за O(log N/8192).


Ты спрашивал про RLE. В ClickHouse сжатие — поколоночное, и run'ы разных колонок не co-aligned (границы не совпадают). Поэтому ClickHouse не выполняет вычисления на сжатых данных — он распаковывает гранулу в блок по 8192 значения, обрабатывает векторно, выбрасывает, идёт дальше


Модель: параллельные массивы по row_id
Таблица с N строками — это фактически N логических row_id от 0 до N-1. Каждая колонка хранится как отдельный массив длины N, где элемент с индексом i — это значение этой колонки в строке с row_id = i.

text
row_id:      0      1      2      3      4     ...
order_date: [d0,    d1,    d2,    d3,    d4,   ...]   ← файл A
order_id:   [42,    17,    99,    3,     56,   ...]   ← файл B
category:   [Book,  Elec,  Book,  Elec,  Book, ...]   ← файл C
price:      [9.99,  199.,  14.5,  89.,   7.2,  ...]   ← файл D
Формально: для каждого i кортеж (A[i], B[i], C[i], D[i], ...) — это одна строка исходной таблицы. Колонки связаны только через индекс i. Между собой файлы A, B, C, D никак не связаны — разные .bin, разные .mrk, разные кодеки, разные гранулы.

ПО СУТИ ФИКСИРОВАНЫЙ ORDER BY. если нужно делать по другому столбцу B - то только создавать новую таблицу отсортированную по .



=================== избыточность данных компенсируется сжатием;


Пример из документации: event_time DateTime CODEC(DoubleDelta, LZ4) — сначала DoubleDelta убирает избыточность временных меток, затем LZ4 жмёт результат
Избыточность компенсируется сжатием
Формально
Денормализация вводит функциональные зависимости row_id → value, где value повторяется многократно. В 3NF эти повторы устраняются через справочники и FK. В ClickHouse они остаются, но не занимают места пропорционально числу повторов.

Ключевое: сжатие в колоночной СУБД зависит от кардинальности колонки, а не от числа строк. Если колонка category имеет k = 10 уникальных значений на N = 10⁹ строк, сжатый размер — O(k), а не O(N).

Три механизма
1. Локальность значений (следствие ORDER BY)

ORDER BY задаёт физический порядок строк. Колонки, входящие в ключ сортировки, монотонны или сгруппированы: все category = 'Books' лежат подряд. Это превращает колонку в последовательность длинных runs одинаковых значений. Кодеки (Delta, DoubleDelta, RLE-подобные) жмут такие последовательности в O(число runs), а не O(N).

2. Колоночные кодеки (encoding)

Двухступенчатый стек:

Первый уровень — преобразование под тип данных: Delta/DoubleDelta для монотонных, T64 для транзитивных, LowCardinality для словарного кодирования, Gorilla для float. Убирает структурную избыточность.

Второй уровень — общий компрессор (LZ4/ZSTD) поверх результата. Убирает остаточную энтропию.

3. Колоночное хранение (независимость)

Каждая колонка сжимается своим кодеком, оптимальным для её типа и распределения. category (10 значений) и order_datetime (почти монотонна) жмутся по-разному, но обе — хорошо. В row store такое невозможно: строка — единица сжатия, и «слабые» поля портят сжатие «сильных».









Delta и DoubleDelta
🔺 Delta (разностное кодирование)
Назначение: Целочисленные типы, DateTime, Date — колонки, значения которых монотонны или слабо меняются от строки к строке.

Алгоритм:

Первое значение блока записывается как есть (base).

Для каждого следующего значения x_i вместо самого значения пишется разность с предыдущим: d_i = x_i - x_{i-1}.

Полученный поток разностей сжимается общим компрессором (LZ4/ZSTD).

Суть: Если данные монотонны, разности малы и лежат в узком диапазоне. Энтропия потока разностей резко падает: вместо «широких» значений пишутся «узкие» дельты. Это классическое differential encoding — уменьшение алфавита за счёт устранения тренда.

Обратное преобразование: prefix sum — x_i = base + Σ d_j. Не требует распаковки всего блока, может считаться потоково.

🔻🔺 DoubleDelta (разность разностей)
Назначение: DateTime, timestamps с равными или почти равными интервалами — метрики, логи, события с фиксированным шагом.

Алгоритм:

Первое значение — base.

Первая разность — d_1 = x_1 - x_0 (аналог Delta).

Для каждого следующего значения пишется разность разностей: dd_i = (x_i - x_{i-1}) - (x_{i-1} - x_{i-2}).

Поток dd_i сжимается общим компрессором.

Суть: Если интервалы постоянны (x_i - x_{i-1} = c для всех i), то все dd_i = 0. Поток превращается в последовательность нулей — сжимается почти в ноль. Если интервалы почти постоянны (шум ±несколько секунд), dd_i малы и лежат в узком диапазоне.

Это второй порядок differential encoding: Delta убирает линейный тренд, DoubleDelta убирает постоянный шаг (линейный тренд самих дельт).

Обратное преобразование: две последовательные prefix sum. Первая даёт d_i, вторая — x_i

 T64 (Transpose 64)
Назначение: Целочисленные типы (Int*, UInt*), DateTime, Date, Enum, Decimal — данные, значения которых лежат в узком диапазоне.

Алгоритм:

Блокировка: Берутся 64 последовательных значения, которые упаковываются в битовую матрицу размером 64x64.

Вычисление диапазона: Для блока находятся минимальное (min) и максимальное (max) значения. На основе этой разницы определяется количество бит (b), необходимое для представления любого значения из диапазона (по сути, ceil(log2(max - min + 1))).

Обрезка бит: Каждое значение преобразуется в value - min, и все старшие биты, выходящие за пределы b, отбрасываются, так как они одинаковы для всего блока.

Транспонирование: Полученная матрица 64 x b транспонируется. Это группирует одноименные биты всех 64 значений вместе, что значительно улучшает сжатие на следующем этапе.

Сжатие: Результат передается общему компрессору (LZ4 или ZSTD).

Суть: T64 устраняет избыточность, вызванную общими старшими битами, и упаковывает данные в компактный битовый поток, который затем эффективно сжимается.

📚 LowCardinality (Словарное кодирование)
Назначение: Строковые типы (String, FixedString) с небольшим количеством уникальных значений (рекомендуемый порог — менее 10 000).

Алгоритм:

Построение словаря: Для колонки строится словарь, содержащий все уникальные значения. Каждому уникальному значению присваивается целочисленный индекс.

Замена значений: Вместо самого значения в каждой строке сохраняется этот целочисленный индекс. Размер индекса (UInt8, UInt16 и т.д.) выбирается в зависимости от размера словаря, что делает его очень компактным.

Сжатие: На диске хранится словарь (уникальные строки) и поток индексов (маленькие целые числа). Оба компонента сжимаются отдельно и очень эффективно.

Суть: Многократно повторяющиеся длинные строки заменяются короткими целочисленными идентификаторами, что drastically сокращает объем хранимых данных и ускоряет операции сравнения и группировки.

🦍 Gorilla (XOR-сжатие)
Назначение: Числа с плавающей точкой (Float32, Float64), особенно в монотонных временных рядах (например, метрики CPU, показания датчиков).

Алгоритм (на основе XOR):

XOR: Для каждого текущего значения x_i вычисляется побитовый XOR с предыдущим значением x_{i-1}: xor = x_i XOR x_{i-1}.

Анализ XOR: В полученном xor-значении подсчитывается количество ведущих (leading) и замыкающих (trailing) нулей. Центральная часть, содержащая значимые биты, кодируется.

Компактная запись: Вместо полных 64 или 32 бит записывается только информация о количестве ведущих нулей, длине значимой части и сами значимые биты. Если значения равны (xor == 0), это кодируется специальным битом.

Суть: Если соседние значения float-чисел близки, их битовые представления также близки. XOR-разность будет содержать много нулей в начале и конце, что позволяет сжать её до нескольких бит вместо 32/64.


То есть при PARTITION BY - мы живем только с данными в пределах одного условия. Для других значений этого условия можно сказать создаются "отдельные БД" (не физически, а по логике).
